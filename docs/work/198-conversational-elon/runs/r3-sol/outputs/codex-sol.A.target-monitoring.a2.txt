I’d start with a **dead-man’s-switch alert for `nightly-sync`**. Central logs can help diagnose failures, but they won’t tell you the job silently stopped unless we add monitoring.

Keep cron and the Python script on `edna`. Wrap the script so the monitoring works even when Python crashes at startup:

- Send a “started” ping when cron launches it.
- Send a “success” ping only if the script exits successfully.
- Send a “failure” ping if it exits with an error.

Set the monitor to expect the daily 03:00 run, with a grace period based on its usual duration. It should email you if the job fails, never starts, or starts but never finishes. That would have caught the expired token on the first night, independently of the script’s summary email.

**My recommendation is hosted Healthchecks.io for that alert.** It stays outside your home network, so it can also notice when `edna`, your internet connection, or your NAS goes down. We should deliberately test a failed run and a missing run before relying on it.

If you want everything self-hosted, Healthchecks can run in Docker on the Synology. That works, but a NAS or home-network outage could take down both the job and its monitor; you’d still want an external check watching the monitor.

For one scheduled job, I’d defer the central logging stack. Keep a rotating log on `edna` for troubleshooting, and put a short error excerpt in the failure notification. You shouldn’t have to read logs to find out whether your sync ran.
