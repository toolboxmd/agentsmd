**Requirements and who asked:** You (just now) need to know within hours, not days, when `nightly-sync` dies, without reading logs.
**Deleted:** A Synology Docker log stack (Loki/Grafana/Dozzle-style central logging). You have one job on one machine; aggregating logs across services solves a problem you don't have, and a log store doesn't alert you on its own, so it wouldn't have caught last week's silence either.
**Bottleneck:** The only alert path today is the email the script sends at the very end, so any crash before that point (like the expired token) is invisible. Fix needs to live outside the script, at the point it's invoked.
**Checked myself:** Based only on what you told me, one cron job on edna, crash was pre-email, nothing else monitors it.

Recommend wrapping the cron invocation itself so cron (not the script) sends an alert on any nonzero exit or crash, regardless of where `nightly-sync` dies: `0 3 * * * /path/nightly-sync.py || echo "nightly-sync failed $(date)" | mail -s "nightly-sync FAILED" you@... ` (swap in a push notification instead of mail if you don't trust your Mac's mail setup to deliver). No new host, no Docker, no Synology involved. If you also want protection against cron or edna itself silently not running at all, the next-smallest step up is a dead-man's-switch ping service (script pings a URL on success, you get alerted if the ping doesn't arrive) rather than a self-hosted log stack, but I'd only add that if plain failure-on-exit isn't enough for you.
