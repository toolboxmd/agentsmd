I’d ship this week by running the existing Python command on your always-on Linux machine with a systemd timer. The missing runs point to the laptop being asleep; the successful exports suggest the command itself is working.

For this setup, there’s no need to split workers and scheduler across services:

- **Execution:** a systemd service runs the Python command in a pinned virtual environment.
- **Scheduling:** a systemd timer runs it overnight, with `Persistent=true` to catch a missed run when the machine comes back online.
- **Deployment:** a small versioned directory containing the script, dependencies, and service/timer files.

Schedule it comfortably before 08:00, add a bounded retry on failure, and alert if that day’s report hasn’t been produced by 07:30. Keep logs in the systemd journal. Safe reruns make recovery straightforward.

Future-proof it by keeping the command independent of systemd, accepting an explicit report date, and returning a nonzero exit code on failure. Those same properties make it easy to move into Airflow later.

Airflow on Kubernetes becomes useful when you have dependent jobs, substantial parallel work, or multiple workflows to coordinate. Budget makes it affordable, but for this three-minute export it adds operational work without fixing anything that the always-on host and a reliable timer can’t handle.
