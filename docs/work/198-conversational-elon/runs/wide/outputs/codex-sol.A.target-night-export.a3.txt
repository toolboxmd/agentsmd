I’d ship this week by moving the existing command to your always-on Linux machine and running it with a systemd timer. The missing runs point to the laptop sleeping; successful runs already produce the right report.

For this workload, the split is simple:

- **Worker:** one systemd service running the Python command under a dedicated user.
- **Scheduler:** one systemd timer, perhaps at 07:00, with `Persistent=true` to catch a missed run when the machine comes back online.
- **Deployment:** a pinned Python environment, the script, and the two unit files on the Linux machine.

Add logs, a bounded retry on failure, and an alert if that day’s report hasn’t arrived by 07:30. Test a normal run, a failed run, and recovery after a missed schedule before shipping.

Airflow on Kubernetes adds components to operate without solving a current requirement. Budget doesn’t change that tradeoff. Future-proof this by keeping the export independently runnable, configuration external, and reruns safe. If you later need dependent jobs or several workers, that same command can become an Airflow task without rewriting the export.
