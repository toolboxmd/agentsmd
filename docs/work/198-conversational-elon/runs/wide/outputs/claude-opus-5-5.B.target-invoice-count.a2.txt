You want the unpaid-invoice count to return in under a second and include every committed invoice at request time. I recommend against Kafka, CQRS and Redis for this: a projection fed by events is eventually consistent, so it can miss invoices committed just before the request, which breaks that requirement. It would also add services and topics to run when the likely cost is the endpoint loading every row and building objects just to count them.

The smallest fix is to replace that with a single `SELECT count(*) ... WHERE customer_id = $1 AND status = 'unpaid'` in PostgreSQL, plus a partial index on `customer_id WHERE status = 'unpaid'` if `EXPLAIN ANALYZE` shows a scan. That reads committed data at request time and could ship this week; the Kafka budget can go to a need that actually requires event streaming.
