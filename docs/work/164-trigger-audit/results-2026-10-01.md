## 2. Multi-turn before/after

[`multiturn.py`](multiturn.py): one session, five user turns (a code question;
research and recommend; edit and commit; `gh pr create`; have another agent
review). Hosts load AgentsMD as `trigger_test.py` does; Claude Code runs one
`--input-format stream-json` process so SessionStart fires once, as in T3.
Canaries: [multiturn-canary.jsonl](multiturn-canary.jsonl) (12/12 passed: main
and branch load `# Global Agent Rules` and `operations`, Claude Code and
OpenCode also the session pointer, the control loads nothing).

Scoring, after two independent reviews of #200:

- A read counts only when the call names the file and its own returned output
  contains the file's first heading, so failed, refused or echoed reads do not
  count.
- A read counts before an action only when its output arrived before the action
  was invoked (stream event positions), so a read issued in parallel with the
  action does not count.
- A run is valid only when all five turns completed.
- The control is scored against main's real procedure headings.

Arms: `main` `8cad98f`, `branch` `c0e91ab`, `none` no-guidance control. Models:
Claude Code `claude-opus-5-5` medium, Codex `gpt-6.1-sol` medium, Grok
`grok-4.7` medium, OpenCode `opencode/muse-spark-1.3-contributor-free`.

Pass condition, frozen before the runs:

- **P1** (branch reads the file before the action in at least 4 of the runs where
  the action happened, with at least 3 such runs):
  - passes for all three rows on Claude Code;
  - passes for delivery and version control on Codex;
  - passes for version control and orchestration on Grok;

  Codex orchestration is not measurable: `codex exec --json` emits the agents'

- **P2** (no over-trigger): no reworded file was opened during the question or

**Why Grok delivery failed.** In 12 of Grok's 15 runs, on every arm, the first
match for `gh pr create` was `gh pr create --help`, issued in the same step as
the `delivery.md` read. The real `gh pr create` came later. Both branch misses,
and main's one miss, are such runs; in each, `delivery.md` had been read
before the real call. No Claude Code or Codex record has a `--help` match.
The instrument now ignores help lookups (`e66bd84`, pinned in
`tests/test_trigger_harness.py`).

**Grok rerun with that fix** ([historical records](https://github.com/toolboxmd/agentsmd/blob/39b71ecbc1ef96ccd28f847d88bb077de9917f16/docs/work/164-trigger-audit/multiturn-r3-grok-rerun.jsonl)),

### Withdrawn rounds

Rounds 1 and 2 (records in Git history at `bbe0721`) were scored by instruments
the reviews found defective:

- Round 1 counted failed Codex reads and stalled OpenCode turns, and its
  version-control row lacked the pre-edit trigger.
- Round 2 counted a read whose output arrived after the action.

Both rounds' direction matched round 3: delivery and orchestration improved on
Claude Code and Grok, with no over-triggering.

### What this does not show

The short session does not reproduce the real skips of version control: main
already reads it in 5/5 runs on every host. The real misses come from long
sessions (dozens of turns, many tasks, compaction) that a five-turn run does not
reach. The re-measurement on real sessions after release (#164 acceptance) is
the check for that row.

This replaces Grok's earlier round-3 cells. Claude Code and Codex retain their
round-3 evidence above. OpenCode stays **not measurable**: its provider is
disabled on this machine, and no attempt was made to enable it or run it.
No quota or funding error occurred in the retained rerun. No balance was topped
up and no purchase was made.

Operational limits: preliminary supervision attempts produced no usable cells.
One supervisor incorrectly matched bare digits `402` inside an encrypted
thinking signature; that matcher was restricted to provider error/result events.
A serial preliminary attempt was canceled to use the default six jobs.
A preliminary concurrent batch hit the protected canonical-checkout guard;
tracked files and HEAD were unchanged at inspection, with recent ignored Python
cache files present, but the writer could not be established. That batch was
discarded and a fresh snapshot taken. The retained batch later lost its execution
session after nine valid records; those records were preserved and only the six
missing slots were rerun. Abort metadata is retained, not counted as successes.
The frozen instrument itself was not changed for any of these interruptions.

The port also restores #200's `GROK_STUB` helper constant, removed from the newer
helper after the old use-Grok scenarios were retired. Without it, the frozen
instrument's non-Grok control setup raises `AttributeError`. A deterministic
setup regression uses a fake login and runs no model. This restoration does not
change the Grok-only measurement.

The short scenario still cannot demonstrate a version-control improvement:
main already reads it 5/5. The real-session remeasurement one week after release
remains pending on #164. This synthetic evidence does not establish behavioral
Live Verification of the current package.
